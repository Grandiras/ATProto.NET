## [Unreleased]

### Breaking changes

- **`AtProtoScopes.Repo(...)` now throws `ArgumentException` for `RepoAction.None`** (Issue #94) — an omitted `action=` list means the full default set in the scope grammar, so `AtProtoScopes.Repo("app.bsky.feed.post", RepoAction.None)` returned `repo:app.bsky.feed.post` — a create + update + delete grant, the exact opposite of the zero-write one the caller asked for. The grammar has no marker for an empty action list, so the request is inexpressible rather than narrow and both overloads now reject it, matching `AtProtoScopes.Space(...)`. Migration: a caller that passed `RepoAction.None` was silently requesting full write access — either drop the `repo:` scope entirely if no record writes are needed, or name the narrowest action that is (`RepoAction.Create`, `Update`, or `Delete`). `RepoAction.All` and every partial combination are unaffected

### Added

- **Spaces: integration tests against a real permissioned-data PDS** (Issue #93) — #89 landed the protocol with 212 unit tests, every one of which stubbed the HTTP layer: the cryptographic constructions pinned against the reference implementation's own outputs, the wire shape against hand-written JSON. That proves the SDK agrees with a *reading* of the specification, not that a server accepts what it sends. `tests/ATProtoNet.IntegrationTests/` now carries 26 tests that talk to a live space host, behind a `[RequiresSpacesFact]` gate that skips unless `ATPROTO_TEST_SPACES=true` — CI is unaffected, as with `[RequiresJetstreamFact]`.
  - **`SpaceNetworkFixture`** provisions three accounts through the admin API and deletes them again, because a space is a three-party arrangement a stub cannot tell apart: an authority that owns the space and mints credentials, a member whose repo is read across the repo boundary, and an outsider the authority must refuse. Each test creates its own space, so the suite is order-independent. `ATPROTO_PLC_URL` points DID resolution at the test network's own directory — a credential is exchanged with, and a commit verified against, whatever the DID document says.
  - **`SpaceCredentialTests`** — the two-hop exchange end to end, including that the server accepts the `htu` the SDK puts in its DPoP proof, which a stub by definition cannot tell us. Then the refusals that make the credential worth something: a replayed delegation token, a token presented for another space, a proof signed by another key, a proof addressed to another host, a credential presented as a bearer token, and `SpaceDeleted` on renewal after `deleteSpace`.
  - **`SpaceRepoSyncTests`** — the CAR round trip, which is the highest-value one: records written through `createRecord`, fetched with `getRepo`, and verified with `SpaceRepoCar.Verify` against the server's own commit and index. It checks that the SDK's LtHash, commit-context encoding, MAC, and canonical DAG-CBOR ordering agree with a real implementation rather than with a reimplementation of the same spec. Then incremental sync over a real oplog: replay to the signed commit, resumption from a persisted cursor, divergence detection, and the fallback to full recovery when `since` is no longer serviceable.
  - **`SimpleSpacePolicyTests`** — a non-member refused under `member-list`, an app refused under `#allowList`, the retry that discovers a space wants a client attestation, revocation taking effect at the next renewal, and the repo boundary holding between two accounts on the same host.
  - **`docs/testing-spaces.md`** documents how to stand a host up. No PDS release serves `com.atproto.space.*` — it lives on [bluesky-social/atproto#5187](https://github.com/bluesky-social/atproto/pull/5187) — so until an image exists the host is a `dev-env` network built from that branch, which is what these tests were run against.

- **`atproto-lexgen` understands `"type": "space"` Lexicon definitions** (Issue #92) — a space type declaration is a Lexicon document whose `main` definition is a `space` rather than a `record`, and the generator did not know about it in either direction: a space-type Lexicon produced an empty file and no diagnostic, and there was no way to declare one from C# at all
  - **JSON → C#.** A `space` definition emits a static holder (`com.atmoboards.forum` → `ForumSpace`) exposing the `Nsid` constant, a `SpaceTypeDeclaration Declaration` built from the schema, and `Key` / `Name` / `LocalizedNames` / `Collections` forwarders onto it — the model the SDK already ships, so the generated type drops straight into `AtProtoScopes.Space(...)` and a consent screen. `key`, `name`, and `collections` are `required` on that model, so a declaration missing one still emits code that compiles (`"any"`, the raw NSID, and an empty set) and says which field it substituted for
  - **C# → JSON.** `atproto-lexgen lexicon` now emits a `space` definition for every static `SpaceTypeDeclaration` an assembly exposes, taking the NSID from a sibling `Nsid` (or `SpaceType`) string constant — the shape the `csharp` command generates, so a declaration round-trips. A declaration with no NSID to attribute it to is reported rather than guessed at, through the new `LexiconEmitter.Warnings`, which also catches two types claiming the same definition instead of silently keeping whichever was reflected over last
  - **Diffing.** `atproto-lexgen diff` compares the declaration, and the collection list is the load-bearing part: a bare `space:` grant resolves its default collection set from the declaration **as it stands when the grant is evaluated**, not as it stood when the user consented. Adding a collection therefore widens every grant already issued (reported, non-breaking) and removing one narrows them (breaking). Key changes are breaking; the consent-screen `name` and its localizations are reported as non-breaking
  - **An unrecognized definition type is now a `WARN` line** naming the NSID and the type, instead of an empty file that reads as "nothing to generate". Definition types that are legitimate input but emit no standalone C# — `query`, `procedure`, `subscription`, and the scalars used as shared property constraints — are unchanged and stay silent

- **Spaces: server-side support in `ATProtoNet.Server`** (Issue #91) — #89 landed the *client* half of the permissioned data protocol: an application can create spaces, read and write records, obtain credentials, and sync. What it could not do was *serve* a space. This is the other half — the ASP.NET Core layer over the `ATProtoNet.Spaces` primitives that lets a .NET service act as a **space authority**, a **repo host**, or both, which is what a PDS is. Registered with `AddAtProtoSpaces()` plus `AddSpaceAuthority<T>(key)` / `AddSimpleSpace<T>()` / `AddSpaceRepoHost<T>()`, and mapped by the ordinary `MapXrpcEndpoints()`. The three halves register separately on purpose: a route that answers is a route that has to be secured, and a service that only needs to *verify* — a moderation service, a proxy — takes `AddAtProtoSpaces()` alone
  - **DPoP proof verification** (`DPoPProofValidator`) — the SDK could only *generate* proofs. Six checks, each of which matters: the signature verifies against the proof's **own** embedded `jwk`, which proves nothing on its own since an attacker can embed any key; that key's thumbprint matches the credential's `cnf.jkt`, which is what makes the first check mean something; `ath` matches the credential actually presented; `htm`/`htu` match the request as received, so a proof captured by one repo host cannot be replayed at another; `iat` is recent; and the `jti` has not been seen. `htu` is compared with query and fragment stripped per RFC 9449 §4.3, so one proof covers any query on a path — which is what lets a client mint a proof before it has built the query string. An `htu` that is not an absolute URL is refused outright rather than compared as the raw string it arrived as: normalization of scheme, host, and port is what makes that comparison mean anything, and a value that skips it has been checked against nothing. A proof whose header leaks its private key is rejected rather than helpfully verified against the public half, and `alg` is pinned to the key's curve rather than taken on trust
  - **Delegation token verification** (`SpaceDelegationTokenVerifier`) — the audience check is the one carrying the weight: `aud` must equal `spaceHostAud(spaceDid)` for the authority named in the token's **own** `sub`, derived from the token and never taken from the request. An authority handed a token minted for a *different* authority therefore cannot present it there. Plus expiry, verification against the issuer's `#atproto` key from its DID document, and single use through the replay store — consumed **last**, only once every other check has passed, so a forged token cannot burn the `jti` of one a legitimate holder is about to present
  - **Space credential verification** (`SpaceCredentialVerifier`) — the repo host's side of the read path. The signer is resolved from the **space URI** rather than from the credential's own `iss`, so nobody but a space's authority can mint credentials for it, with `#atproto_space` taking precedence over `#atproto` when an authority publishes one. A repo host does not re-evaluate the authority's access decision and has no way to: it holds no member list, and the protocol enumerates no readers
  - **Client attestation verification** (`SpaceClientAttestationVerifier`) — resolves the `client_id` to its `client-metadata.json`, follows `jwks_uri` when the keys are not inline, and verifies against the key the attestation's `kid` names. Trying every published key instead would let a client with one compromised key keep attesting under another, so an attestation with no `kid` is accepted only when the client publishes exactly one key. The fetch is directed by the attestation, so it is `https`-only and bounded by `MaxClientMetadataBytes` whether or not the server declares a length
  - **`ISpaceReplayStore`** with an in-process default — single-use enforcement for delegation tokens, client attestations, DPoP proofs, and service auth, keyed on `(iss, jti, exp)` rather than on the `jti` alone: two issuers picking the same nonce is not a collision, and including the expiry is what lets an entry be evicted once the token it guards would be rejected on its own expiry anyway. **Replace it with a shared store** in a multi-instance deployment, or a replay is caught only by the instance that saw the original
  - **`SpaceServerOptions.MaxSingleUseTokenLifetime`** (five minutes by default) caps how far ahead the `exp` of an inbound single-use token — a delegation token, a client attestation, a service auth token — may sit. All three are minted to live 60 seconds, but the `exp` on one presented here is whatever its signer chose, and the signer is only checked against what it is claiming *after* the token has been accepted. Bounding it bounds both how long a captured token stays replayable and how long its `jti` occupies the replay store, which evicts an entry only once the token it guards has expired anyway. Service auth additionally rejects an `iat` dated in the future
  - **Key resolution reads every verification-method type the SDK understands.** #98 taught the core to read the legacy `Ecdsa...VerificationKey2019` entries that older PLC releases and hand-written `did:web` documents publish alongside `Multikey`; the space verifiers now go through that same lookup, so an authority is not accepted or refused depending on whether the presented token happened to carry a `kid`. Key material that turns out to be malformed is a failed verification rather than a fault: the document belongs to the party being verified, so it is reported under the caller's own error name instead of escaping as a `FormatException`
  - **The endpoint surface** — `getSpaceCredential`, `listRepos`, `registerNotify`, `unregisterNotify`, and `notifyWrite` on the authority side; `getRecord`, `listRecords`, `getLatestCommit`, `getRepo`, `listRepoOps`, `getBlob`, and `listBlobs` on the repo side, over an `ISpaceRepoHost` an application implements. Returning `null` produces `RepoNotFound`, which deliberately does not distinguish a member who has never written from an account that is not a member at all — the protocol carries no reader set, and saying more would leak membership. `getBlob`'s reference check **is** its access check: serving a blob on the basis of its CID alone would hand out any blob an account holds to anyone with a credential for any of its spaces
  - **`com.atproto.simplespace.*`** — all seven administration methods over an `ISimpleSpaceStore`, plus `SimpleSpaceAccessPolicy`, the baseline policy evaluated at mint time. Two perimeters, both of which must pass: the user policy (`MemberListPolicy` / `PublicPolicy` / `ManagingAppPolicy`, the last calling `checkUserAccess` out to the managing app with service auth) and the app access policy (`OpenAppAccess` / `AllowListAppAccess`, evaluated against the **attested** client ID and nothing else, which is what makes an allow list enforceable rather than advisory). The app perimeter is evaluated first, so an unattested client is told to attest before any managing-app call is made. A `ManagingAppPolicy` whose app is unreachable **refuses**: failing open would turn every outage of the app into an open space. Deletion flags a space rather than removing it, because a deleted space has to keep answering `SpaceDeleted` on renewal — that is how a syncer that missed the notification learns to drop its copy, and one that simply vanished would answer `SpaceNotFound`, which says nothing
  - **Write notification delivery** (`SpaceWriteNotifier`) — fans `notifyWrite` and `notifySpaceDeleted` out to the registered services with service auth, resolving each subscriber's endpoint from the service fragment it registered. Best-effort by design: a failure is logged and dropped rather than queued, because the syncer's periodic sweep over `listRepos` is the correctness guarantee and the notification is only the latency optimization. `EnsureAuthoritySubscribedAsync` auto-registers a space's authority on the first write into a shared space, which is what puts an account into the writer set at all — an authority learns who holds data in its spaces only from the notifications it receives, and receives them only because it is registered to. Inbound, `NotifyWriteEndpoint` accepts a notification only from the host that actually answers for the named repo
  - **`SpaceServerOptions.PublicBaseUrl`** is not optional behind a reverse proxy. A DPoP proof names the URL it was minted for and the verifier compares it against the request *as received*, which behind a proxy is an internal `http://` name no client could have named
  - Covered by **105 new unit tests**, including a `TestServer` end-to-end pass over the real HTTP surface: the credential exchange, then a repo read authenticated with the credential it produced. The negative cases are the point — a delegation token minted for another authority, a credential signed by an authority that does not gate the space, a stolen credential presented with the thief's own key, a proof minted for another host or another credential, a replayed token, a client attestation signed by a key the client does not publish
  - `docs/spaces.md` gains a *Serving a space* section, with `docs/api-reference.md` and `docs/architecture.md` updated

- **XRPC handler routing: named errors and binary responses** (Issue #91) — two additions to `ATProtoNet.Server.Xrpc` that the space endpoints needed and any handler can use. `XrpcException(error, message, statusCode)` thrown from a handler is caught by the routing and written as the `{"error", "message"}` body XRPC clients actually branch on, rather than escaping as a 500; it carries a `Headers` dictionary for things like the `WWW-Authenticate` a DPoP endpoint owes a rejected request. `IXrpcBlobQuery<TParams>` is the counterpart of `IXrpcQuery<,>` for Lexicon methods whose output `encoding` is not `application/json` — `getBlob`, `getRepo`, the CAR-serving sync methods — streaming the body rather than buffering it. Query-parameter binding failures now answer `InvalidRequest` instead of throwing, and `XrpcBooleanConverter` binds a Lexicon `boolean` parameter from the text a query string carries

- **Spaces: the permissioned data protocol** (Issue #89) — AT Protocol is not one protocol but several, and the one everyone knows is only half of it. Public broadcast publishes signed, redistributable records that anyone may crawl. [Permissioned data](https://atproto.com/blog/atproto-spaces-alpha) ([proposal 0016](https://github.com/bluesky-social/proposals/tree/main/0016-permissioned-data)) is the other half: the same shape — DID-based authority, per-user repositories, Lexicon-typed records, applications crawling hosts to build views — with an access perimeter around it, called a **space**. It is what bookmarks, drafts, subscriber-only posts, private forums, and group chats need and public broadcast cannot give them. This is an alpha proposal, not a final specification; it has had no security review and provides **access control, not confidentiality** — the data is not end-to-end encrypted, and every service that handles it can read it, which is what makes server-side search, indexing, and moderation possible at all
  - **`SpaceUri` / `SpaceRecordUri`** — `at://{authority}/space/{type}/{skey}[/{author}/{collection}/{rkey}]`. Permissioned data reuses the `at://` scheme rather than defining its own, and the literal `space` marker sits where a collection NSID appears in a public URI; the two can never be confused, because an NSID always contains at least two dots and `space` contains none (`SpaceUri.IsSpaceUri`). Authority splits in two here, which is the one structural difference from a public AT-URI: the URI's authority is the **space** authority that gates access, while the record's authority remains the **author** DID that wrote and signed it. Neither may be a handle — a space's identity and membership are keyed on DIDs
  - **`LtHash`** — the homomorphic set hash a permissioned repo commits to, in place of a Merkle Search Tree root. Each record expands to 1024 little-endian `uint16` lanes via BLAKE3 XOF, summed into a 2048-byte state mod 2^16. Addition and subtraction commute, so the digest depends only on the *set* of records a repo holds and never on write order, and a write is one cheap pass over the lanes rather than a recomputation. Verified lane-for-lane against the reference implementation's own primitives, including a non-ASCII element that would catch a UTF-16 encoding
  - **BLAKE3 in XOF mode**, implemented from scratch because .NET ships no BLAKE3 and the SDK carries no third-party cryptography dependency. Checked against 27 of the reference implementation's own test vectors — input lengths from 0 to 102400 bytes, each compared over 131 bytes of extended output, so the chunk tree and the XOF stream are both exercised
  - **`SpaceRepoCommit` / `SignedSpaceCommit` / `SpaceCommitVerifier`** — a commit is deliberately **not** a rebroadcastable proof of what its author wrote. The signature covers only the context (space, author, revision, and 32 fresh random bytes), never the digest; the digest is bound to that context by a *symmetric* MAC keyed from those public bytes. A reader in the sync flow gets full authenticity and integrity, while anyone holding a leaked commit can compute a valid MAC for any digest they like, so it proves nothing. A fresh nonce per `Sign` means two commits over identical state differ, which is what stops a commit becoming a stable fingerprint. The TLS-style context encoding (big-endian length prefixes — the opposite byte order from the LtHash lanes, and the thing most likely to be silently "fixed" to match the surrounding code) and the `HMAC-SHA256(HKDF-Expand(ikm, ctx, 32), hash)` MAC both match the reference implementation byte-for-byte
  - **`SpaceRepoCar`** — the two-root CAR form `getRepo` serves: the signed commit, then a DAG-CBOR index mapping `{collection}/{rkey}` to each record's CID, with the record blocks following in the same canonical order. That layout is what lets `Verify` validate the whole thing in one pass — verifying the commit makes its digest trustworthy, folding the index into a set hash authenticates every path/CID pair *without reading a single record*, and each block is then checked against a CID the index already vouched for. `excludeValues` yields an index-only CAR that still authenticates, for diffing against a local copy
  - **`SpaceCredentialProvider` / `SpaceReader` / `SpaceTokens`** — the credential exchange, end to end. Reaching a space turns on two independent axes: **which user** is being acted for, established by a delegation token the user's PDS mints, and **which application** is acting, established by a client attestation the application signs itself. They are presented together but signed by different parties and evaluated independently. A credential is **not a bearer token** — it reads a whole space and is presented to every repo host in it, so as a bearer token a host given one to serve its own repo could replay it against every other host. It is DPoP-bound at issuance to a freshly generated key the provider discards when the credential expires. Whether a space requires a client attestation is not advertised, so the provider asks without one and retries only on an `AppNotAuthorized` refusal. Credentials are cached per space and renewed ahead of expiry; one credential obtained through any single user's session serves an application's whole user base
  - **`SpaceSyncer` / `SpaceRepoCursor` / `ISpaceRepoStore`** — there is no relay for permissioned data, because permissioned repos are non-rebroadcastable by construction and no intermediary can collate a firehose of them. An application pulls from each repo host directly. A pass walks the operation log from the cursor's revision, applying each entry to the caller's store and to a running set hash; at the head of the log the response carries the repo's signed commit, and comparing digests is what says whether the copy is exactly current. That comparison — rather than having received every individual operation — is what makes sync **self-healing**: a dropped write, a compacted oplog, and a locally corrupted copy all surface identically as a digest mismatch, and all are repaired identically by falling back to a full download. A `since` the host can no longer serve is likewise an expected condition rather than an error, since the oplog is a transport optimization with no history guarantee and does not survive account migration
  - **`com.atproto.space.*`** on `AtProtoClient.Space` — the full endpoint surface, grouped by who serves it: `getDelegationToken` / `listSpaces` / `createRecord` / `putRecord` / `deleteRecord` / `applyWrites` on the user's PDS; `getRecord` / `listRecords` / `getBlob` / `listBlobs` / `getLatestCommit` / `getRepo` / `listRepoOps` on whichever host holds the repo; `getSpaceCredential` / `listRepos` / `registerNotify` / `unregisterNotify` on the space authority; `notifyWrite` / `notifySpaceDeleted` for delivery. `listRepos` returns the **writer set** — accounts that have written at least one record — which is the sync boundary and not an access-control list; readers are never enumerated at the protocol level
  - **`com.atproto.simplespace.*`** on `AtProtoClient.SimpleSpace` — the space-management implementation every PDS must support, so an application has a baseline to build against without standing up a bespoke space service. `createSpace` / `updateSpace` / `deleteSpace` / `getSpace` / `addMember` / `removeMember` / `listMembers`, plus `checkUserAccess` for applications implementing the managing-app side. A user must be authorized by the user policy (`MemberListPolicy`, `PublicPolicy`, or `ManagingAppPolicy`, which defers to an app per request and so enables follower-gating or subscription checks without an explicit list) **and** their app by the app access policy (`OpenAppAccess` or `AllowListAppAccess`, evaluated against the *attested* client ID)
  - **`AtProtoScopes.Space(...)`** with `SpaceAction` and `SpaceManage` — `space:` OAuth scopes, granted by space *type*, which is the consent boundary. `authority` defaults to `self`, so a bare grant covers only the user's own spaces of that type. Read access is all-or-nothing at the space boundary, so the read actions ignore the collection list — and the distinction between the two read grants is the one that matters: `Read` also confers `getDelegationToken` and therefore the whole space, while `ReadSelf` confers the same methods for the holder's own repo only and cannot reach past it, which is the right grant for an export or backup tool. `SpaceAction.None` is rejected rather than emitted: an omitted action list means the full default set and the grammar has no marker for an empty one, so silently eliding it would hand back the full read/write grant a caller asking for zero record access was trying to avoid
  - **`SpaceAuthority`** resolves `#atproto_space` and `#atproto_space_host` from a DID document, each falling back to `#atproto` and `#atproto_pds` — which is what makes any ordinary account a usable space authority for personal data with no DID-document change at all. **`SpaceTypeDeclaration`** reads the `"type": "space"` Lexicon definition, including the localized `name` a consent screen shows in place of the raw NSID. **`LexBytesJsonConverter`** handles the AT Protocol JSON data model's `{"$bytes": "…"}` wrapper, which the commit's four byte fields travel in
  - Documented in the new `docs/spaces.md`, with `docs/api-reference.md`, `docs/index.md`, `docs/architecture.md`, and `README.md` updated. New `samples/SpacesSample` walks personal data, the set-hash sync comparison, and the credential exchange. The endpoints have no unit-test-friendly server, so the wire shape, the sync state machine, and every cryptographic construction are covered by 212 unit tests instead — the LtHash digests, commit context encoding, and MAC pinned against values generated by the reference implementation's own libraries

- **`JetstreamEventParser.ParseFrame(ReadOnlyMemory<byte>, JetstreamProtocol)`** (Issue #87) — a no-copy counterpart to the `ReadOnlySpan<byte>` overload, for callers that already hold the frame on the heap. `JsonDocument` cannot parse a span without first copying it, so the span overload allocates a duplicate of every frame; the memory overload reads the buffer in place. `JetstreamClient`'s receive loop now uses it, which takes ~600 bytes per event off the live tail. The span overload is unchanged and still correct for stack-allocated input
- **Jetstream v2 archive: replay and snapshot** (Issue #85) — the live tail is one of three ways to consume Jetstream v2; the other two are the HTTP archive, which between them cover what an indexer actually needs — *the records that already exist* **and** *every new one*, with no gap at the seam. `JetstreamReplayConsumer.ReplayAsync()` backfills history and then cuts over into the live tail in a single `await foreach`, in sequence order
  - **`JetstreamSegmentReader`** — a decoder for Jetstream's sealed segment format (`.jss`): the 256-byte fixed header, the run of length-prefixed zstd frames, and the columnar block body (event count, the fixed-width `seq` / `witnessed_at` / `indexed_at` / `kind` / length columns, then the concatenated `collections` / `dids` / `rkeys` / `revs` / CBOR payload columns). `ReadRowsAsync` / `ReadEventsAsync` stream a segment block by block rather than materializing it — segments run to hundreds of megabytes — and `DecodeBlockFrame` decodes a single frame as `getBlock` returns it. `JetstreamArchiveRow` exposes the archive's own shape, including the untouched CBOR the network published, so a mirror stays byte-auditable; `ToEvent()` projects to the same `JetstreamEvent` model the live tail delivers, computing a commit's CID from its payload (the archive stores no CID column) and applying the `indexed_at == 0 → witnessed_at` display-time fallback. Verified against Jetstream's own golden fixtures: `segment/testdata/golden_block.bin` and the fixed header of a real sealed segment, both from the reference implementation
  - **`JetstreamArchiveClient`** — typed wrappers for `planSnapshot`, `listSegments`, `getSegment`, and `getBlock`, with `Authorization: Bearer`, HTTP `Range`, and ETags. The endpoints are metered in **response bytes on the wire**, so the retry behaviour is part of the contract: a `429` (`byte limit exceeded`) waits out exactly the `Retry-After` it was given, and `DownloadSegmentAsync` resumes an interrupted transfer with a `Range` request from the exact byte offset it stopped at rather than re-fetching (and being re-charged for) what it already has. A server that ignores the `Range` and answers `200` truncates and restarts instead of concatenating a duplicated prefix. `JetstreamArchiveException` carries `StatusCode`, `Error`, `RetryAfter`, and `IsRetryable`, so a revoked key (`401`) is not retried while an exhausted quota is
  - **The plan loop pins the tip.** The first `planSnapshot` response's `sealedTipSeq` becomes the ceiling for the whole backfill, and each later page resumes at `plannedThroughSeq` with that ceiling as `beforeSeq`, so the range cannot float while it is being downloaded — and `BeforeSeq` caps that ceiling, so a bounded snapshot stops where it was asked to even when `sealedTipSeq` is far above. A page that comes back *without* advancing while the ceiling is still ahead — the sealed tip reported before the segments carrying it are servable — is re-planned after an exponential wait, `MaxStalledPlanAttempts` times (default 5), and then fails with a `JetstreamArchiveException`; ending the backfill below the pinned tip instead would be a permanent silent gap, since the cutover reconnects at that tip and neither phase would ever deliver the skipped range. Planned work units download with `DownloadParallelism` in flight but decode strictly in plan order, whole segments spooled to a temporary file rather than buffered. The planner works from bloom filters and per-block summaries — no false negatives, but it can return blocks with no matching rows — so the exact `WantedDids` / `WantedCollections` / `WantedKinds` filter is applied again to what was decoded, with the live tail's semantics: collections constrain commit events only, and account-level events reach a collection-filtered consumer
  - **The cutover is inclusive and deduplicated.** The live socket is connected once at the pinned tip, which the server replays inclusively, and events at or below the last sequence number already delivered are dropped. If the backfill ran long enough that the tip aged out of the socket's 36-hour lookback window, the refused connect (`JetstreamConnectException`) sends the consumer back into the plan loop from the last sequence number it delivered — up to `MaxCutoverAttempts` times — rather than skipping the gap
  - **`JetstreamConsumerOptions.Archive`** (new `JetstreamArchiveOptions`) configures all of it: `ApiKey`, `BlockDecompressor`, `AfterSeq`, `BeforeSeq`, `SnapshotOnly`, `DownloadParallelism`, `SpoolDirectory`, `MaxRetryAttempts`, `MaxRetryDelay`, `MaxCutoverAttempts`, `MaxStalledPlanAttempts`, `ServiceUrl`, `HttpClient`. The filters and the `CursorStore` are shared with the live tail, since a replay cursor *is* the v2 sequence number the live consumer already persists — one store spans both phases and a restart resumes the backfill where it stopped. `SnapshotOnly` stops when the archive is exhausted; `BeforeSeq` bounds a snapshot above and requires it, since there is nothing to cut over into above a fixed ceiling
  - **`IJetstreamBlockDecompressor`** is a separate seam from `IJetstreamDecompressor` on purpose: segment blocks are plain zstd frames with **no dictionary**, so a decompressor with the Jetstream WebSocket dictionary loaded cannot read one. The SDK still bundles no zstd. The segment checksum is likewise not recomputed locally — it is an xxh3 metadata checksum, exposed as `JetstreamSegmentHeader.Checksum` / `JetstreamSegmentInfo.Checksum` (also the `getSegment` ETag) for the comparison a mirror actually needs, because sealed segments are immutable only *between* compactions and a rewritten file gets a new checksum
  - **`JetstreamArchiveTests`** (`tests/ATProtoNet.IntegrationTests`) exercises the endpoints against a live instance — segment listing, a pinned plan window, a `getBlock` frame decoded end to end, a ranged `getSegment` whose header matches the listing, the `401` for a bad key, and a bounded snapshot replay. Gated by the new `RequiresJetstreamArchiveFact` (`ATPROTO_JETSTREAM_API_KEY` on top of `ATPROTO_TEST_JETSTREAM=true`) and deliberately small, since the endpoints bill real bytes. New `samples/JetstreamReplaySample` shows the ZstdSharp block decompressor, snapshot mode, and the replay cutover; `docs/jetstream.md` replaces its *Historical Replay* placeholder with the full flow and `docs/api-reference.md` lists the new types
- **Jetstream v2 is now supported alongside v1** (Issue #83) — Jetstream's second wire protocol serves at `/xrpc/network.bsky.jetstream.subscribeEvents` under the `xrpc.v1.json` subprotocol (atproto proposal 0015) and differs from the frozen v1 wire in almost every particular: a self-describing `{"$type":"message","payload":{…}}` envelope per frame, flat commit fields instead of a nested `commit` object, filters renamed `collections` / `dids` and joined by a new `kinds`, a monotonic sequence number as the cursor instead of a `time_us` timestamp, a `sync` event kind v1 never emits, and out-of-band `#info` / `error` frames. `JetstreamClient` and `JetstreamConsumer` speak both, selected by the new `JetstreamConsumerOptions.Protocol`
  - **`Protocol` defaults to `JetstreamProtocol.V1`**, so every existing configuration keeps its endpoint, its parameter names, and its timestamp cursor with no change. The legacy `jetstream1`/`jetstream2` hosts serve v1 only; the two v2 hosts serve both, so an existing v1 configuration can be pointed at `JetstreamEndpoints.UsEast` without touching anything else
  - `JetstreamEndpoints` — `UsEast` / `UsWest` (the v2 instances) and `LegacyUsEast1` / `LegacyUsEast2` / `LegacyUsWest1` / `LegacyUsWest2`, rather than having every caller paste host names
  - **`WantedKinds`** (`IReadOnlyList<JetstreamEventKind>`) — the v2 `kinds` filter. A collection filter constrains *commit* events only, and identity/account/sync events flow regardless on both protocols, so a commits-only stream needs `WantedKinds = [JetstreamEventKind.Commit]` as well. Combining `WantedCollections` with a `WantedKinds` list that excludes `Commit` is a filter that could never apply, and now throws `ArgumentException` before the socket opens rather than coming back as an HTTP 400
  - **`JetstreamSyncEvent`** — a repo resynchronization marker (broken commit chain; drop the account's derived state and re-read it), carrying `Rev` and the commit CAR in `Blocks`, decoded from the wire's `$bytes` wrapper. Only v2 emits these; a consumer that folds the stream into a store should handle them the way it handles an account deletion
  - **`JetstreamEvent.Cursor`** — Jetstream's sequence number, and the v2 resume position. Also populated on the v1 wire from the `cursor` field the v2 hosts added to it, and null against a legacy instance. Unlike `TimeUs` it is unaffected by an operator timestamp import, so it is always a faithful resume position. `JetstreamEvent.Timestamp` exposes `TimeUs` as a `DateTimeOffset`; on v2 both are derived from the frame's RFC 3339 `time`, whose six fractional digits convert exactly
  - **Cursor handling follows the protocol.** `JetstreamConsumer` tracks the v2 sequence number as `LastCursor` (`LastTimeUs` still tracks v1), persists whichever the protocol uses, and reconnects at exactly the last sequence number it delivered — a v2 cursor is replayed *inclusively* by the server, so `ReconnectRewind` has nothing to rewind past and is ignored. A v2 event that somehow carried no sequence number is not persisted, since storing its timestamp would hand the server a resume position it reads as a sequence number
  - **A rejected subscription is no longer retried in a loop.** v2 validates before the WebSocket upgrade and answers a stale cursor (`CursorTooOld`), a retired dictionary (`UnknownZstdDictionary`), or a malformed filter with an HTTP 400. `JetstreamClient` now surfaces that as the new `JetstreamConnectException` (with `StatusCode` and `IsRetryable`), and `JetstreamConsumer` persists its progress and rethrows instead of reconnecting — retrying is futile and dropping the cursor would silently skip the gap the caller is supposed to backfill
  - **`OnInfo` / `OnStreamError`** — v2's `#info` advisories (e.g. `OutdatedCursor`) and terminal `error` frames (e.g. `ConsumerTooSlow`) are neither events nor exceptions. They are logged and passed to these callbacks; an error frame ends the connection and the consumer reconnects as it would after any drop
  - **`JetstreamDictionaryClient`** — v2 frame compression is dictionary-versioned, so the subscription must name the dictionary ID it was built against. This fetches `network.bsky.jetstream.getZstdDictionary` and reads the ID out of the zstd dictionary's own header (RFC 8878 §5), so one call yields both halves of the new `ZstdDictionaryId` + `Decompressor` pair. Setting only one of the two now throws: an ID without a decompressor asks for binary frames nothing can read, and a decompressor without an ID has no version to name. The SDK still ships no zstd implementation — the `IJetstreamDecompressor` seam is unchanged
  - `JetstreamEventParser.ParseFrame(json, protocol)` is the new entry point, returning a `JetstreamFrame` (event, info, or error) so the non-event frames have somewhere to go. The existing `Parse(...)` overloads are unchanged and still read the v1 wire. Both wires stay forward-tolerant: an unknown envelope, message type, or operation is skipped rather than throwing
  - Historical replay was left out of that change and landed separately — see the archive entry below (Issue #85)
  - **`JetstreamV2Tests`** (`tests/ATProtoNet.IntegrationTests`) checks the protocol against a live instance rather than a script: commit parsing and the `kinds` / `collections` filters, monotonic sequence cursors, inclusive cursor replay, the pre-upgrade 400 for a cursor below the retention floor (`CursorTooOld`) and for a retired dictionary (`UnknownZstdDictionary`), the dictionary fetch and its self-describing ID, and the v1 wire served by a v2 host. Gated by the new `RequiresPdsFact`-style `RequiresJetstreamFact` (`ATPROTO_TEST_JETSTREAM=true`, host overridable with `ATPROTO_JETSTREAM_URL`), so they skip in CI, which has no outbound internet, and need neither a PDS nor credentials when run. Documented in `docs/jetstream.md` (new **Protocol Versions**, **Advisory and error frames**, and **Historical Replay** sections), `docs/api-reference.md`, `docs/index.md`, and `README.md`

### Changed

- **Performance and memory pass over the streaming, repository, and CID hot paths (Issue #87)** — no public behaviour changes; the one API addition is listed above. Measured on a 4693-byte `#commit` frame, a 1000-entry MST, and a 1000-block CAR, with tiered compilation disabled (median of three runs):

  | Operation | Time before → after | Allocated before → after |
  | --- | --- | --- |
  | `FirehoseEventParser.Parse` (one `#commit`) | 147 µs → 22 µs (**6.6×**) | 102 KB → 29 KB (**3.5×**) |
  | `MerkleSearchTree.Create` (1000 entries) | 3.44 ms → 0.61 ms (**5.7×**) | 743 KB → 161 KB (**4.6×**) |
  | `MerkleSearchTree.Get` × 1000 | 3.10 ms → 0.10 ms (**31×**) | 362 KB → **0** |
  | `CarReader.FindBlock` × 1000 | 6.10 ms → 0.03 ms (**187×**) | 40 KB → **0** |
  | `CidComputation.EncodeCidToString` | 88 ns → 67 ns (**1.3×**) | 432 B → 144 B (**3×**) |
  | `MerkleSearchTree.Serialize` (1000 entries) | 961 µs → 903 µs | 1348 KB → 1190 KB (**1.13×**) |

  - **`FirehoseEventParser` transcodes DAG-CBOR straight into the JSON the models bind from**, instead of decoding to a `JsonElement`, re-serializing that into a `JsonNode` tree, rewriting the tree, copying it into a fresh discriminator-first object, and serializing *that* for the deserializer — five passes over every frame. The rewrite also deep-cloned at every level, so a `#commit`'s base64 `blocks` string was re-copied once per level of nesting above it. The single pass writes byte strings with `Utf8JsonWriter.WriteBase64StringValue`, so the CAR blob never becomes a UTF-16 string at all. `$type` is written first rather than spliced in afterwards
  - **`CarReader.FindBlock` builds a CID index on first use** rather than scanning every block. Resolving a repository's MST is one lookup per node, so the linear scan made a repo walk quadratic — and exports run to tens of thousands of blocks. The index is deferred (callers that only enumerate `Blocks` never pay for it) and keyed by a span-comparing comparer, so a lookup allocates nothing. A repeated CID still resolves to its first occurrence, as the scan did
  - **`MerkleSearchTree.Get` and `TryUpdate` no longer call `List.IndexOf` on the entry they are iterating** — a linear rescan per comparison, from the front, making a single-node probe quadratic in the node's entry count. `Get` and `Remove` also computed the key's depth (a SHA-256) on entry and never used it, so a tree walk hashed the key once per node visited; lookups now allocate nothing at all
  - **`MerkleSearchTree.Create` hashes each key once.** The layer recursion recomputed every key's depth at every layer and copied the entry range into fresh lists as it partitioned, costing *n* × maxDepth hashes and as many temporary list entries; depths are computed once up front and the recursion works on index bounds into the shared arrays. `MstKeyDepth.ComputeDepth(string)` encodes to a stack buffer instead of allocating one per call, and both MST serializers carry the previous key's encoded bytes forward rather than re-encoding it
  - **`CidComputation.EncodeCidToString` builds the string in one pass** — `"b" + Base32Lower.Encode(...)` allocated a `char[]`, a string from it, and a third string for the concatenation. `CarBlock.CidHex` uses `Convert.ToHexStringLower` rather than allocating an upper-case string to lower-case it
  - **The WebSocket read loops take a single-receive fast path.** `FirehoseClient` and `JetstreamClient` staged every message through a `MemoryStream` and then `ToArray()`d it; almost every frame arrives whole in the 64 KB buffer, and is now copied straight out of it. Multi-frame messages still spool as before
  - **`CarReader.FromStreamAsync` parses the buffer it already filled** instead of `ToArray()`ing a second copy of the whole CAR onto the large object heap
  - **`FirehoseVerifier.ExtractSignedView` writes the unsigned commit into one exact-sized array.** The spliced length is known before the copy, so the growing `MemoryStream` and the `ToArray()` off it are both gone. `WriteMapHeader` now takes a `Span<byte>` and returns the bytes written, alongside a new `MapHeaderLength`
  - **`AtProtoJsonDefaults.Options` is initialized by the type initializer** rather than by a `??=` on first read, which could let concurrent first calls each build their own instance — and every `JsonSerializerOptions` carries a separate reflection-derived contract cache. The instance stays mutable until first use, as before, so a startup-time `AtProtoJsonDefaults.Options.Converters.Add(...)` keeps working
  - **`XrpcClient` joins the `atproto-accept-labelers` header once** when the subscription is set, not on every request. `DagCborEncoder` takes an array's length from `GetArrayLength()` instead of materializing a list to count it, and sorts object keys in place. `Did.Method` slices the value rather than `Split(':')`-ing it into an array to return one element

### Fixed

- **`SpaceSyncer` reported `Partial` forever for a member who had never written to the space** (Issue #99) — `SyncRepoAsync` treated a missing commit as "the page stopped short of the head of the oplog, sync again to continue", which is one of two ways to get one. The other is an account with no repo state: the host builds the commit from that state, so `listRepoOps` answers `{ops: [], commit: undefined}` for such an account rather than refusing the read. The pass then applied nothing, advanced nothing, and reported `Partial` — the outcome documented as "the caller should sync again to continue" — so a caller looping on that contract spun on the repo forever. `Partial` is now reported only when the pass has somewhere left to go (it applied operations, or the host offered a continuation cursor); a page carrying neither is reported as `SpaceSyncOutcome.NoRepo`, the same answer `getRepo` gives by refusing outright. A cursor already standing at a revision takes the existing repair path instead, since the host reporting no state for a repo the caller holds a copy of is exactly what full recovery resolves — `RepoNotFound` drops the stale copy, and a repo that does exist rebuilds it. A syncer driven from `listRepos` never saw this, since the writer set only contains accounts that have written; one walking a member list, or holding a stale writer-set entry, did. No signature changed and no new enum member was added
- **DID document signing keys are read from the legacy verification-method types too** (Issue #98) — both places the SDK pulled a signing key out of a DID document required `type == "Multikey"`, so against a document publishing the older `EcdsaSecp256k1VerificationKey2019` / `EcdsaSecp256r1VerificationKey2019` form the key came back as absent: `SpaceSyncer.ResolveSigningKeyAsync` threw `SpaceRepoVerificationException("'{did}' publishes no AT Protocol signing key")` and no permissioned commit could be verified at all, and `FirehoseVerifier` treated every commit from that account as unverifiable. The two encodings differ by more than the type string — a `Multikey`'s `publicKeyMultibase` is base58btc over multicodec-tagged *compressed* key bytes, while the legacy form is base58btc over a bare *uncompressed* point (`0x04 || X || Y`) with no multicodec prefix — so the point is now compressed by the parity of Y and re-tagged with the curve the type names, which is what the reference implementation's `getKey` does. plc.directory serves `Multikey`, so production `did:plc` was never affected; the reference `dev-env` network's pinned `@did-plc/lib` and hand-written `did:web` documents publish the legacy form. The conversion lives in one place rather than at each call site: **`VerificationMethod.ToDidKey()`**, **`DidDocument.GetSigningKey()`** and **`DidDocument.GetVerificationKey(fragment)`** (new public API), over the new **`AtProtoCrypto.FormatDidKey(publicKey, curve)`** and **`AtProtoCrypto.CompressPublicKey(publicKey)`**. `SpaceAuthority.GetSigningKey` and `FirehoseVerifier` both go through them, and `SpaceNetworkFixture` in the integration tests drops the private resolver it needed to work around this, so the space commit-verification tests now assert against the production path
- **DAG-CBOR map keys were sorted bytewise rather than length-first** — DRISL orders map keys by length and only then by bytes, so `{"b":…,"ab":…}` must encode `b` before `ab`. `DagCborEncoder` sorted them by plain ordinal comparison, which agrees with the canonical order only when no two keys differ in length. Every CID the SDK computed for a record whose keys spanned more than one length was therefore wrong — an `app.bsky.feed.post` carrying both `text` and `createdAt` among them — so a locally computed CID would not match the one the rest of the network computed for the same record. `DagCborDecoder`'s matching validation had the same rule and would have rejected valid blocks. Both now use the canonical comparison, which is also what the new permissioned-repo index depends on. Regression-pinned against a post fetched from a live PDS alongside the CID that PDS reported for it
- **DPoP proofs named the full request URL in `htu`** — RFC 9449 §4.2 requires `htu` to be the request URI with its query and fragment stripped, and a verifier compares against exactly that. `DPoPProofGenerator` passed the URL through unchanged, so every proof for a request carrying a query string — which is every XRPC query — named a `htu` no conforming resource server would match. The proof is now normalized to origin plus path, which also means one proof covers any query on a given path
- **XRPC array query parameters are now sent as repeated keys instead of one comma-joined value** — 21 call sites across the Lexicon clients built `?dids=a,b` where XRPC specifies `?dids=a&dids=b`, so any endpoint taking an array silently saw a single malformed element. Affected: `app.bsky.feed.getPosts` (`uris`), `getFeedGenerators` (`feeds`), `app.bsky.actor.getProfiles` (`actors`), `app.bsky.labeler.getServices` (`dids`), `app.bsky.graph.getRelationships` (`others`), `getStarterPacks` (`uris`), `com.atproto.admin.getAccountInfos` (`dids`), `com.atproto.label.queryLabels` (`uriPatterns`, `sources`), `chat.bsky.convo.getConvoForMembers`/`getConvoAvailability` (`members`), `tools.ozone.signature.searchAccounts` (`dids`), and the eight array filters on `tools.ozone.moderation.queryEvents`/`querySubjects`. `AdminClient.GetAccountInfosAsync` was building the correct repeated-key list and then discarding it in favour of the comma-joined value. Callers passing a single element are unaffected; callers passing several were getting results for one bogus identifier and now get what they asked for
- **`RecordCollection` list operations no longer hand back records whose `Value` is null** — `ListAsync`/`ListFromAsync` (and the `EnumerateAsync` pair built on them) suppressed a failed deserialization with `value!`, so an entry that did not match `T` surfaced as a `RecordView<T>` violating its own `required T Value` contract and threw a `NullReferenceException` somewhere downstream. They now throw `InvalidOperationException` naming the offending record URI and target type, matching what `GetAsync` already did
- **A failed per-request client build no longer leaks an ECDSA key handle** — `AtProtoClientFactory.CreateClientForUserAsync` constructed the `AtProtoClient` and the DPoP `OAuthSessionResult` before `ApplyOAuthSessionAsync` took ownership of them; if that call threw, nothing disposed either and the native key handle survived until finalization. Both are now disposed on the failure path
- **`FileAtProtoTokenStore` writes are atomic and deletes are serialized against them** — `StoreAsync` wrote in place, so a crash or a concurrent read mid-write could leave a truncated file and lose the refresh token; it now writes a temp file and moves it into place. `RemoveAsync` deleted outside the `SemaphoreSlim` that guards writes, so a logout racing a token rotation could leave the just-written file behind; it now takes the same lock. Token files are also created owner-only on Unix rather than inheriting the process umask
- **XRPC error responses that are not an XRPC error envelope now keep their body** — the fallback `AtProtoHttpException` discarded the response text it had already read, leaving `ResponseBody` null exactly when the message was least useful. The parse failure is also no longer caught with a bare `catch (Exception)` that would have swallowed unrelated errors
- **Non-integral query parameters are formatted with the invariant culture** — `AtProtoClient.QueryAsync` renders parameter values through `IFormattable`, so a client running under a culture such as `de-DE` no longer sends `1,5` where the server expects `1.5`
- **`Cid.Parse`/`TryParse` documentation matches what they do** — both were described as validating, and the type carried a compiled `GeneratedRegex` that nothing ever called. The dead regex is gone and the summaries now say plainly that only null/blank input is rejected
- **`AtProtoClientFactory` no longer claims a refresh that does not happen** — a comment stated the XRPC client refreshes on-demand when it receives an `ExpiredToken` error; no such logic exists anywhere in `XrpcClient`, so per-request clients silently never refreshed. The comment now describes the actual contract (call `RefreshSessionAsync` and retry; the rotated token is persisted via the store passed to `ApplyOAuthSessionAsync`)
- **`README.md` and `docs/` audited against the actual public API** (Issue #74) — every type, method, parameter, and constant named in the documentation was cross-checked against `src/` and `tools/`, and the ones that had drifted were corrected. The larger ones: `docs/crypto.md` documented an `AtProtoKey.Generate` / `AtProtoCrypto.EncodeMultikey` / `GenerateDidKey` / `Base58Encode` surface that does not exist (the real API is `AtProtoCrypto.GenerateP256Key`, `key.ToMultikey()`, `key.ToDidKey()`, `AtProtoCrypto.FromMultikey`/`FromDidKey`), showed `ServiceAuthGenerator.CreateToken` as a static method, and described the MST as taking string CIDs with a `byte[] Serialize()`; `docs/standard-site.md` omitted the repository argument every `StandardSiteClient` method takes and used record fields that were never in the Lexicon models (`PublicationRecord.Theme`, `SubscriptionRecord.Subject`, `BasicTheme.PrimaryColor`); `docs/ozone.md` named the moderation events `ModerationEvent*` instead of `ModEvent*`. ### Added

- **Managed PDS** — Run the official Bluesky PDS as a container your app owns, and administer it from .NET. This replaces the removed in-process PDS: the reference implementation does the serving, ATProto.NET does the orchestration and administration
  - `PdsAdminClient` (core `ATProtoNet`, namespace `ATProtoNet.Admin`) — administers any PDS you hold the admin password for, authenticating with HTTP Basic as the reference PDS expects. `CreateAccountAsync` is the headline: it calls `describeServer`, mints an invite code with the admin credentials when the server requires one, and then signs the account up — so an app can provision accounts on its own server rather than sending users to an external provider. The signup call itself is sent unauthenticated, so the admin password is never attached to a public endpoint. Also wraps invite codes (`CreateInviteCodeAsync`, `CreateInviteCodesAsync`), account lookup, takedown/restore, handle/email/password updates, and deletion; `Admin` and `Server` expose the raw admin-authenticated clients for everything else. The constructor rejects a non-loopback `http://` URL rather than sending the admin password in the clear
  - `PdsAdminOptions.AllowInsecureHttp` — opt-in for reaching the PDS over plaintext HTTP at a non-loopback host, the shape an Aspire container network produces. Default `false`; the guard validates the *effective* base address, so supplying an `HttpClient` whose `BaseAddress` differs from the configured URL cannot slip past it
  - `AddAtProtoPdsAdmin()` (`ATProtoNet.Server`) — registers `PdsAdminClient` as a typed `HttpClient`, binding `AtProto:Pds:Url`, `AtProto:Pds:AdminPassword`, and `AtProto:Pds:AllowInsecureHttp` (the keys the Aspire integration supplies). Overloads take explicit credentials or a `PdsAdminOptions`. Missing configuration throws while the host is built, naming the key; the client's own validation — such as the refusal to send the admin password over plaintext HTTP — runs when it is first resolved. Registering it as a typed client rather than a singleton over one captured `HttpClient` means the factory rotates the underlying handler, so a long-running deployment picks up DNS changes behind the PDS URL
  - `WithAtProtoPds(pds)` (`ATProtoNet.Aspire.Hosting`) — wires a project to the PDS container in one call: `WithReference`, the configuration keys above, and `WaitFor` on the container's health check. In run mode it also sets `AtProto__Pds__AllowInsecureHttp`, because a containerized consumer resolves the PDS over the container network rather than at a loopback address and would otherwise be rejected by the very URL this method supplies. It does **not** set it when publishing: sending the admin password unencrypted across a deployed network is left as the operator's explicit decision
  - `WithHandleDomains`, `WithInviteCodeRequired`, `WithAdminPassword`, `WithJwtSecret`, `WithPlcRotationKey`, `WithDataBindMount` — new configuration methods on the PDS resource. `AdminPasswordParameter`, `JwtSecretParameter`, and `PlcRotationKeyParameter` are exposed on `AtProtoPdsContainerResource`

  - `WithHostname` gained a `ParameterResource` overload, and the PDS hostname is now resolved through the resource like the other settings. Running locally it defaults to `localhost`; when publishing there is no sensible default, so `AddAtProtoPds` creates a `{name}-hostname` parameter for the deployment to supply. The hostname fixes the server's `did:web` identity and the domain new handles are created under, so a PDS deployed as `localhost` would issue identities nothing can resolve
  - `PDS_DEV_MODE=true` is likewise set only when running locally. Left unset in a published manifest, the container defaults it off, so dev-mode's relaxed checks cannot reach a deployment by inheritance
  - **Overriding a generated parameter now removes it from the application model** — `WithHostname`, `WithJwtSecret`, `WithPlcRotationKey`, and `WithAdminPassword` create their parameters before any override can run, so a superseded one stayed in the model and appeared in a published manifest as an input. A deployment was prompted for a hostname or secret nothing would read
  - **CI now runs both untested seams.** A `pds-integration` job starts the real `ghcr.io/bluesky-social/pds` container as a service and runs `PdsAdminTests` (gated by `[RequiresPdsAdminFact]` / `ATPROTO_PDS_ADMIN_PASSWORD`) against it: describe, invite minting, account provisioning, handle updates, takedown/restore, deletion, and signing in with the session a provisioned account was handed. A second step publishes the AppHost sample's manifest and asserts on it with `AspireManifestTests` (gated by `ATPROTO_ASPIRE_MANIFEST`), covering the publish path that needs no container runtime. Both jobs set `ATPROTO_REQUIRE_INTEGRATION=1`, which turns a skipped gate into a failure: `dotnet test --filter` exits 0 when every test it matched skipped, so a drifted environment variable would otherwise leave a green check that verified nothing — the exact failure this PR exists to correct
  - New documentation page `docs/managed-pds.md` and samples `samples/ManagedPdsSample` (a signup API built on `PdsAdminClient`) and `samples/ManagedPdsSample.AppHost` (the Aspire AppHost wiring it to a PDS container). ### Fixed

- **`WithDataBindMount` produced a container that could not start** — `AddAtProtoPds()` always mounts a named volume at `/pds`, and `WithDataBindMount` added a second mount on the same destination. Both annotations reached the container spec, which Docker and Podman reject outright (`Error: /pds: duplicate mount destination`), so the documented `AddAtProtoPds("pds").WithDataBindMount("./pds-data")` never came up. Supplying a data mount now replaces the default one instead of adding to it. `WithDataVolume(name?)` is added as the counterpart, for renaming the volume or restoring it after a bind mount
- **The Aspire PDS container never started** — `AddAtProtoPds()` set `PDS_DATA_DIRECTORY` but no blobstore, and the reference PDS exits during startup with `Must configure either S3 or disk blobstore`. It now sets `PDS_BLOBSTORE_DISK_LOCATION` to `/pds/blocks`, under the same data volume, so blobs persist with the rest of the server's state. Present since the integration was introduced in 0.4.0, and not caught earlier because nothing ran the container
- **Seven `AdminClient` methods threw `JsonException` against a real PDS** — `DeleteAccountAsync`, `UpdateAccountHandleAsync`, `UpdateAccountEmailAsync`, `UpdateAccountPasswordAsync`, `DisableAccountInvitesAsync`, `EnableAccountInvitesAsync`, and `DisableInviteCodesAsync` requested a deserialized response (`ProcedureAsync<TRequest, object>`) from endpoints the reference PDS answers with an empty body, so every one of them failed with `The input does not contain any JSON tokens` no matter what the server did. They now use the body-only `ProcedureAsync<TRequest>` overload. This also affected the corresponding `PdsAdminClient` wrappers. The same defect affected 19 further procedures elsewhere in the client API; that fix was tracked separately in Issue #69 (see below) so this change stayed scoped to the managed-PDS work it supports
- **Aspire PDS container regenerated its JWT secret and PLC rotation key on every run** — `AddAtProtoPds()` generated both with `RandomNumberGenerator` while the AppHost graph was being built, so each run produced fresh values, but the data volume it mounts persists. Every restart therefore invalidated all existing sessions and, worse, left the accounts already in the volume with `did:plc` identities whose rotation key the server no longer held. Both are now Aspire parameters generated as lowercase hex and persisted to the AppHost's user secrets — stable across runs, matching the volume's lifetime. Override them with `WithJwtSecret` / `WithPlcRotationKey` for production. **Existing volumes were written under a key that was already lost each run**, so a PDS volume from a previous version should be recreated rather than reused. Generation happens in run mode only: the PDS reads both as hex and an Aspire manifest's `generate` instruction can only describe an alphanumeric string, so in publish mode the two parameters carry no default and the value must be supplied at deploy time rather than being generated into something the server would reject
- **XRPC procedures with no declared output threw `JsonException` on every call** (Issue #69) — 19 methods across `IdentityClient`, `SyncClient`, `ActorClient`, `GraphClient`, `NotificationClient`, and the Ozone communication/team/set clients asked for a deserialized response (`ProcedureAsync<TRequest, object>`) from endpoints whose Lexicon declares no output, so the empty body a real server returns failed with `The input does not contain any JSON tokens` before the caller saw anything. They failed on every call regardless of what the server did — and this is not a corner of the API: `PutPreferencesAsync`, the six mute/unmute methods, `UpdateSeenAsync`, `RegisterPushAsync`, and `UpdateHandleAsync` are ordinary client calls. All now use the body-only `ProcedureAsync<TRequest>` overload that already existed. No public signatures change, since each of these methods already returned `Task` and discarded the value
  - The defect survived because the test doubles returned `{}`, which deserializes perfectly well. `EmptyResponseBodyTests` drives all 19 NSIDs through a handler that answers 200 with an empty body, the way a real server does
- **`LoginForm` threw when the app had not called `services.AddLocalization()`** (Issue #35) — The `IStringLocalizer<LoginForm>` support added in 0.4.0 is documented as optional, but it was wired up with `[Inject]`, and Blazor's property injection requires the service regardless of the property's nullable annotation. Rendering `<LoginForm />` in an app without localization registered threw `InvalidOperationException: Cannot provide a value for property 'Localizer' … There is no registered service of type 'IStringLocalizer\`1[…LoginForm]'` before parameters were applied, so passing explicit `ButtonText`/`HandlePlaceholder` values did not avoid it. The localizer is now resolved through `IServiceProvider.GetService<IStringLocalizer<LoginForm>>()`, so it is genuinely optional: without it the built-in English defaults render, with it the copy is localized exactly as before. The `services.AddLocalization()` workaround remains valid
- **`atproto-lexgen csharp` emitted C# that did not compile** (Issue #45) — Found by generating the published `exchange.recipe.*` Lexicons (recipe.exchange) for a third-party appview. All of the following are fixed, with unit coverage in `CSharpEmitterTests`:

  - **CS0542 member/type name collisions** — a `blob` property `image` inside the `image` def generated `BlobRef Image` inside `class Image`. Members that collide with their enclosing type (or with another member, or with `AtProtoRecord`'s `Type`/`CreatedAt`) are renamed — `ImageBlob`, `…Ref`, `…List`, `…Value` — while `[JsonPropertyName]` keeps the wire format unchanged. Lexicon names that are not legal identifiers (`2fa`, `kebab-case`, C# keywords) are sanitized
  - **CS0101 duplicate types** — sibling documents share a C# namespace, so two `#appPassword` defs under `com.atproto.server` collided; later defs are now prefixed with their document name and the rename is reported
  - **Unqualified `BlobRef`/SDK types** — generated files now emit `using ATProtoNet;` / `using ATProtoNet.Models;` only when needed, plus `#nullable enable` and `using System.Collections.Generic;`. Cross-namespace references are rooted at `global::` so a generated namespace such as `Bsky.Generated.Chat.Bsky.Actor` no longer shadows the reference
  - **Non-nullable `JsonElement` fallbacks** — optional members are always nullable; serializing `default(JsonElement)` (`ValueKind.Undefined`) threw
  - **Cross-namespace refs landed in the consumer's namespace** — `app.bsky.embed.defs#aspectRatio` generated `<Prefix>.App.Bsky.Embed.AspectRatio` (a type that does not exist) instead of the SDK's `ATProtoNet.Lexicon.App.Bsky.Embed.AspectRatio`. - **`[JsonPropertyName("$type")]` is now repeated on every `Type` override** (Issue #45) — `System.Text.Json` does not carry the attribute from the abstract `AtProtoRecord.Type` onto an override, so records serialized with hand-built `JsonSerializerOptions` (i.e. without the Issue #49 contract modifier below) emitted a spurious `"type"` field. - **`OAuthClientMetadata` serialized unset optional fields as JSON `null`, so authorization servers rejected the client-metadata document** (Issue #41) — The AT Protocol OAuth spec distinguishes *absent* from *null*, and the reference `@atproto/oauth-provider` fails a document containing `"jwks_uri": null` / `"logo_uri": null` / `"token_endpoint_auth_signing_alg": null` with `invalid_client_metadata`, breaking PAR for any app that served `Results.Json(metadata)` at its `client_id` URL. Every optional property on `OAuthClientMetadata` (`client_name`, `client_uri`, `logo_uri`, `tos_uri`, `policy_uri`, `token_endpoint_auth_signing_alg`, `jwks`, `jwks_uri`) and on the nested `JsonWebKey` (`crv`, `x`, `y`, `kid`, `use`, `alg`) now carries `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`, so the document is spec-compliant under any `JsonSerializerOptions` — including the ASP.NET Core defaults — with no consumer change. The `DefaultIgnoreCondition = WhenWritingNull` workaround remains valid
- **`AtProtoRecord` subclasses serialized a stray `type` property alongside `$type`** (Issue #49) — `AtProtoRecord.Type` is abstract and carries `[JsonPropertyName("$type")]` on the *base* member. System.Text.Json neither inherits that attribute through an `override` nor collapses the base member and the override into one contract property, so a record written the documented way (`public override string Type => "com.example.todo.item";`) emitted **both** a correct `"$type"` and a stray camelCased `"type"` — polluting records that other AT Protocol apps read. A new contract modifier, `AtProtoJsonDefaults.ApplyRecordTypeDiscriminator`, now collapses those duplicates to a single leading `"$type"` on every `AtProtoRecord`-derived type. It is wired into `AtProtoJsonDefaults.Options` and `LexiconTypeRegistry.CreateOptions()`, so `RecordCollection<T>` and `RepoClient` writes are fixed with no consumer change; the workaround of re-declaring `[JsonPropertyName("$type")]` on the override remains safe. Add the modifier to your own `DefaultJsonTypeInfoResolver.Modifiers` if you serialize records with hand-built `JsonSerializerOptions`
- **Implementing `IAtProtoUnion` broke all (de)serialization of records containing the union** (Issue #46) — The internal `UnionJsonConverterFactory` registered in `AtProtoJsonDefaults.Options` and `LexiconTypeRegistry.CreateOptions()` claimed every type assignable to `IAtProtoUnion` from `CanConvert` but returned `null` from `CreateConverter`, which System.Text.Json rejects with `InvalidOperationException: The converter 'ATProtoNet.Serialization.UnionJsonConverterFactory' cannot return a null value`. Marking a custom open-union base with the interface therefore threw on every read and write touching it. The factory never did anything — union discrimination comes from `[JsonPolymorphic]`/`[JsonDerivedType]` plus `LexiconTypeRegistry.RegisterUnionVariant` — so it has been removed. `IAtProtoUnion` remains as a behaviour-free documentation marker; `docs/custom-records.md` gains a "Union Types" section covering closed and open unions
- **`PlcClient` DID-path requests bypassed the directory `BaseAddress`** (Issue #47) — `did:plc:…` strings parse as *absolute* URIs (scheme `did`), so `ResolveDidAsync`, `GetOperationLogAsync`, `GetAuditLogAsync`, `GetLastOperationAsync`, and `GetPlcDataAsync` all failed with `NotSupportedException: The 'did' scheme is not supported` instead of querying `https://plc.directory/<did>`. Requests now use RFC 3986 `./`-prefixed relative references; regression tests added (the class previously had no unit coverage)
- **OAuth handle resolution no longer stalls on a dead handle domain** (Issue #52) — Starting the OAuth flow for a handle whose domain silently drops packets on port 443 blocked for the full 100 s `HttpClient` default before the flow continued, so sign-in appeared to hang. `ResolveHandleToDidAsync` now races the HTTPS well-known lookup against the DNS-over-HTTPS TXT lookup (first DID wins) instead of trying them in sequence, and both it and `ResolveHandleAuthoritativeAsync` bound each round with `HandleResolutionTimeout` (5 s by default) so one unresponsive authority cannot dominate the flow. Caller cancellation still propagates; only budget expiry is treated as "no answer". The appview fallback gets its own fresh budget
- **SDK-created OAuth `HttpClient` no longer inherits the 100 s default timeout** (Issue #52) — `AtProtoOAuthService` now applies `AtProtoOAuthServerOptions.HttpClientTimeout` (30 s) to the client it creates, and only overwrites the `User-Agent` header when one isn't already set. `DidWebResolver`'s parameterless constructor applies a 10 s timeout for the same reason (the target host is embedded in the DID). `AtProtoClient`'s own client is unchanged — it carries blob uploads, where 100 s can be legitimate; pass a pre-configured `HttpClient` to shorten it
- **A timed-out handle probe no longer aborts OAuth sign-in** (Issue #42) — Handle verification in `CompleteAuthorizationAsync` is best-effort: it distinguished failures by exception type, so a refused connection (`HttpRequestException`) left `IsHandleVerified = false` while a *timed-out* probe (`TaskCanceledException` — a parked handle domain, or any host when the `HttpClient` has a `ConnectTimeout`) propagated out and failed the whole login, even though the authoritative DID from the token response's `sub` was already in hand. Both now yield an unverified handle; only the caller's own `CancellationToken` still aborts the flow (and now disposes the pending DPoP key when it does). `VerifyDidToAuthServerConsistencyAsync` likewise reports caller cancellation as cancellation rather than wrapping it in an `auth_server_mismatch`-style `OAuthException`; probe timeouts there still fail closed
- **Polymorphic payloads with a non-leading `$type` failed to deserialize** (Issue #50) — The Bluesky appview serializes embed views (and real-world writers serialize record-internal unions) with the `$type` discriminator anywhere in the object, not necessarily first; System.Text.Json requires `AllowOutOfOrderMetadataProperties` for that. Now set in both `AtProtoJsonDefaults.Options` and `LexiconTypeRegistry.CreateOptions()`, fixing `getPosts`/`getPostThread`/timeline reads that contain embeds (previously threw `NotSupportedException`)
- **`Directory.Build.props` `RepositoryUrl` dropped the `.git` suffix** so Forgejo's NuGet registry can match the URL against the canonical repo URL on first upload. Without this, every new packable project published as an *orphan* (resolvable by `dotnet add package` but absent from the repo's Packages tab in the Forgejo UI), requiring a manual `POST /api/v1/packages/Grandiras/nuget/{name}/-/link/ATProto.NET` to relink after each first release. Affects new packages only; the five v0.4.0 packages already orphaned (`Aspire`, `Aspire.Hosting`, `Pds`, `LexiconGenerator`, `Server.EntityFrameworkCore`) were relinked manually post-release

### Security

- **`/.well-known/atproto-did` responses are now capped and redirect-checked** (Issue #52) — The endpoint lives on a host derived from untrusted user input. Responses are read with `HttpCompletionOption.ResponseHeadersRead` and capped at 1 KiB (by `Content-Length` and during the read, so a chunked body can't bypass it) instead of being buffered in full, and a response whose final request URI landed on a different host than the handle is ignored rather than trusted — a hostile handle domain can no longer redirect resolution at an arbitrary host and have that host's DID accepted. Same-host redirects (http→https, trailing slash) still resolve
- **Handle resolution now queries DNS-over-HTTPS on every attempt** (Issue #52) — Because `ResolveHandleToDidAsync` races the two lookups instead of trying HTTPS first, `dns.google` is contacted for every handle resolution, not only when the HTTPS well-known lookup fails. Deployments that treat the handle being resolved as sensitive should note the additional third-party disclosure. `ResolveHandleAuthoritativeAsync` already queried both on every call

### Fixed

- **OAuth, firehose, and repo correctness pass (F1–F15 + G1–G14 + review follow-up)** — Series of fixes addressing review findings across the OAuth, firehose, and repo subsystems
  - **Commit signature verification (`FirehoseVerifier`)** — Use `CborConformanceMode.Strict` instead of `Ctap2Canonical`. The previous mode forbade all CBOR tags, but DAG-CBOR requires tag 42 for CIDs, so every real commit threw `CborContentException` and verification failed for the wrong reason. Canonical-form integrity is preserved by the byte-for-byte splice of the original buffer
  - **MST canonical form (`MerkleSearchTree`)** — Restored empty parent-layer wrapping in `SplitAndInsert` and added matching empty-parent wrapping in `BuildLayerTopDown` so incremental `Add` and bulk `CreateFromEntries` produce the same root CID as atproto/ts. `Create(entries)` now delegates to `CreateFromEntries` so both public factories use the spec-conformant builder
  - **Firehose at-least-once semantics (`FirehoseConsumer`)** — Reconnect cursor only advances when the consumer calls `Acknowledge(seq)`. When `Acknowledge` is never called, the cursor falls back to the current frame's seq (at-most-once); the docstring spells out the contract explicitly. The monotonic floor is now pre-seeded with the caller's resume cursor so a hostile first frame can't rewind below the intended resume point
  - **CAR block CID codec policy (`CarReader` + `FirehoseVerifier`)** — `VerifyAllBlockCids` now throws on `UnknownCodec` in addition to `Mismatch`. The static `FirehoseVerifier.VerifyCarBlockCids` path also fails closed on `UnknownCodec`, so the cheap pre-check and the full signature path apply the same policy
  - **OAuth refresh persistence (`AtProtoClient`)** — Rotated tokens are written to `IAtProtoTokenStore` BEFORE the in-memory session is mutated. A store-write failure now surfaces immediately rather than silently desyncing memory and disk (the old failure mode left the persisted store with the dead refresh token, logging users out on next process restart)
  - **OAuth refresh token store wired** — `AtProtoClient.ApplyOAuthSessionAsync` gained an optional `IAtProtoTokenStore? tokenStore` parameter that `AtProtoClientFactory` passes through, so refresh-rotated tokens land in durable storage instead of only the per-request `InMemorySessionStore`
  - **Refresh-lock around `ApplyOAuthSessionAsync`** — The session swap now holds `_refreshLock`, preventing a timer-driven refresh from racing the swap and corrupting state
  - **Bounded timer-driven refresh** — `OnRefreshTimerElapsed` uses a 30-second `CancellationTokenSource` so a slow token endpoint can't pin `_refreshLock` indefinitely and block foreground `LogoutAsync`/`ApplyOAuthSessionAsync`
  - **`Dispose` race with timer callback** — Sync `Dispose()` drains in-flight callbacks via `Timer.Dispose(WaitHandle)`; the callback's `Release` is wrapped in `try`/`catch ObjectDisposedException` so a late-firing release on a disposed semaphore can no longer escape `async void` and crash the process. `_oauthSession` and `_refreshLock` are now disposed in `Dispose` and `DisposeAsync`
  - **`LogoutAsync` clears `_oauthTokenStore`** — Defensive cleanup so a subsequent re-login with a different `tokenStore` arg doesn't inherit a stale reference
  - **`OAuthClient` constructed lazily on `IOAuthClientProvider.TryGetClient`** — Only when explicit `ClientMetadata` is configured (the production case). Loopback callers must still drive `StartLoginAsync` to materialize a client, since the loopback `client_id` encodes the live request's callback URL
  - **JWT pre-validator algorithm allowlist (`AtProtoAuthenticationHandler`)** — Now allowlists `ES256`/`ES256K`/`ES384`/`ES512`/`EdDSA`/`RS256`/`RS384`/`RS512`/`PS256`/`PS384`/`PS512` only. Previously only rejected `alg=none`, so symmetric HS256 forgeries reached the PDS unchallenged
  - **Handle resolution requires HTTPS + DNS agreement (`AuthorizationServerDiscovery`)** — `ResolveHandleAuthoritativeAsync` now runs HTTPS well-known and DNS-over-HTTPS lookups concurrently and fails closed when they return different DIDs. (Note: both transports currently share the same TLS trust root via `dns.google` — true authority diversification needs a system DNS path)
  - **`did:web` id comparison is case-insensitive for host** (`AuthorizationServerDiscovery`) — DNS host names are case-insensitive per RFC 1035; the prior strict `Ordinal` compare rejected valid `did:web:Example.com` documents. `did:plc` remains strictly case-sensitive
  - **`AtProtoTokenData` / `OAuthSessionResult` gained `IsHandleVerified`** — Persisted and restored across factory hydration. Default-claims now emit `"handle.invalid"` as `ClaimTypes.Name` when the handle isn't bidirectionally verified, with an explicit `handle_verified` claim alongside the actual `did` and `handle`. **Behavior change for existing OAuth sessions:** tokens persisted before this release deserialize with `IsHandleVerified=false`, so `User.Identity.Name` shows `"handle.invalid"` until users re-login
  - **`TryReadSeq` propagates `OperationCanceledException`** — Previously swallowed by an unfiltered catch, breaking cancellation propagation through the cursor-advance logic
  - **`WriteMapHeader` rejects oversized counts** — Throws `ArgumentOutOfRangeException` on negative counts and now emits the 4-byte (CBOR 0x1a) header for counts ≥ 65536. Previously silently truncated to 16 bits, producing malformed CBOR
  - **`AtProtoClient.Dispose`/`DisposeAsync` releases `_oauthSession` and `_refreshLock`** — DPoP ECDsa key and SemaphoreSlim wait handles no longer leak to GC finalization

- **Packaging & release pipeline** — Release artifact hygiene
  - `Aspire.Hosting` dependency in `ATProtoNet.Aspire.Hosting` upgraded from `9.2.1` to `9.5.2`, picking up `KubernetesClient 17.0.14` and resolving the transitive moderate-severity NU1902 advisory (GHSA-w7r3-mgwf-4mqq)

- **Cryptographic security hardening** — Fixes from security audit of crypto primitives
  - **Low-S normalization** — `NormalizeLowS` was a complete no-op (dead code). Now compares S against the actual curve half-order and computes `order - S` when needed. Prevents signature malleability.
  - **High-S signature rejection** — `Verify()` now rejects signatures with S > half-order, enforcing AT Protocol's low-S requirement
